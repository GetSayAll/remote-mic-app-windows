# 打开微信偶发多出一个登录界面：托盘兜底"重新拉起"会新起实例弹出登录小窗

- 发现日期：2026-10-18（用户反馈 + 2026-10-13→10-17 的用户诊断日志）
- 状态：已修复（本机真机复现 + 修复 + 自动化测试）；**用户端复测待做**（`deferred`）
- 影响范围：微信为预设应用「打开应用」目标的所有版本——含「托盘图标 → 重新拉起 → 定点显示」
  三级兜底之后的版本（2026-10-03 的 60fb569 起）；用户日志出处 v1.0.0
  `source_revision=a4c1311`；与遥控器型号（RC001/RC003）无关；受影响第三方应用：微信 4.x
  （`Weixin.exe`，本机实测 4.1.15.56；用户侧窗口类同为 `Qt51514QWindowIcon` 一族）
- 功能点：按键映射「打开应用」——预设应用「微信」（已运行、窗口收在托盘时唤回）
- 现象：按键打开微信时，有几率**额外弹出一个微信登录/"进入微信"小窗**
  （用户原话："按键设置打开微信，有几率再打开一个登录的界面"）
- 复现条件：
  1. 微信已登录运行，主窗口收进托盘（全部窗口隐藏）；
  2. 按映射为"打开应用（微信）"的按键；
  3. 且这一次**托盘图标路线没能在有界等待（6×200 ms）内把已知窗口唤回**——用户日志里
     9 次里出现 6 次，与"有几率"吻合；
  4. 满足 1–3 时代码会"按应用入口重新拉起"微信，微信随后新起第二个实例弹出登录小窗。
- 正常预期：只把微信主窗口唤回置前，不产生第二个实例、不出现登录小窗
- 证据：
  - **用户日志**（v1.0.0，2026-10-15 08:38、09:15，10-16 09:18，10-17 03:29、08:18、08:20 共 6 次）：
    `phase=tray_icon ... terminal_result=failed` →
    `phase=relaunch_entry reason=window_hidden_by_app visible=0 hidden={1..4}` →
    `phase=launch_target source=start_menu_shortcut` →
    `phase=relaunch_entry terminal_result=failed reason=app_window_not_observed`（重新拉起从未让
    主窗口自己恢复）→ `phase=relaunch_fallback target=largest_hidden_window terminal_result=passed`。
    另有 3 次 `tray_icon ... terminal_result=passed`（走成功路径、无第 6 行事件）。
  - **本机复现**（2026-10-18，Weixin 4.1.15.56）：记录窗口清单后把微信收进托盘
    （主窗口 882×803 隐藏、可见窗口 0），再按产品同款方式重新拉起微信（`Start-Process`，
    与 `launch_explicit` 的 ShellExecuteW 同路径）——
    **约 2.1 s 后新出现一个 Weixin.exe 进程，带一个可见的 295×387 `Qt51514QWindowIcon`
    窗口（"进入微信"登录/入口小窗）；原主窗口全程保持隐藏**；观察到 5.6 s 小窗不消失。
    试验后已关闭该多余窗口（第二个进程退出），微信恢复为托盘的试验前状态。
  - 同一轮本机对照：5 轮"收起 → 按键"探针中托盘图标路线 **5/5 在约 250 ms 内唤回主窗口**
    （本机不产生"托盘失败"分支；缺陷分支由上面的独立实验直接证明）。
- 根因：`RunningWindowDisposition::DelegateToApp`（全部窗口收在托盘）分支在托盘图标路线失败后
  会"按应用入口重新拉起"应用，意图是让单实例应用自己把窗口恢复出来（避免直接 `ShowWindow`
  造成的"点不动"）。**对微信 4.x 该前提不成立**：再次启动不会恢复主窗口，而是新起第二个实例
  并显示登录/入口小窗。2026-10-03 的修复（892e957）只让回落不再选中该小窗，但没有移除
  "重新拉起"这一步，副作用因此保留并在用户环境以"多一个登录界面"出现。
- 修复（`crates/sayall-windows/src/app_launcher.rs`，最小改动）：
  1. 预设表新增 `relaunch_when_hidden: bool`：微信置 `false`（附真机依据注释），其余预设保持
     `true`（未观察到同类副作用，不改变既有行为）；
  2. `DelegateToApp` 分支：该字段为 `false` 时跳过"重新拉起"及其中间等待，直接进入原有
     "定点显示已知主窗口"回落，并落日志
     `phase=relaunch_skipped reason=relaunch_pops_login_window visible=0 hidden=N`；
  3. 回落日志补 `class=` 与 `size=`（只读类名 + 布局尺寸，不含窗口标题）——2026-10-03 Bug
     记录遗留的"无法从日志断言显示的是主窗口还是登录小窗"问题由此可判别。
- 验证：
  - 单元测试先红后绿：`hidden_relaunch_is_skipped_only_for_apps_with_known_login_window_side_effect`
    （微信必须跳过 + 其余预设保持既有行为）；`cargo test --workspace` 全绿（结果见提交说明）；
    `cargo fmt --all -- --check` passed。
  - 真机（本机）passed：① 复现实验（上文）：重新拉起 → 新进程 + 可见 295×387 登录小窗、
    主窗口不恢复；② 托盘图标路线 5/5 唤回主窗口、无第二个进程。
  - **`deferred`**：修复后的用户端复测——需用户把微信收进托盘后按键，新日志应出现
    `phase=relaunch_skipped`，且任务管理器不出现第二个微信进程、不弹登录小窗。本机托盘
    路线稳定成功，"托盘失败 → 跳过重新拉起"的完整链路在本机无法自然触发。
- 已知未封闭边界（均未观测到、不在本次修复范围）：
  1. `StartFresh` 路径（进程在跑、但没有任何"合格窗口"）仍会重新拉起微信——例如主窗口隐藏且
     处于最小化、`GetWindowRect` 退化值被尺寸兜底过滤掉时。用户日志与本机实验都未出现这种
     形态（无 `small_or_unlaid_out class=Qt51514QWindowIcon` 记录）；若同类症状再现，先查这里。
  2. 用户环境"托盘图标路线有时失败"的根因未查明（本机 6/6 成功）。失败时现在落到"定点显示
     已知主窗口"（1.2 s 有界等待之后），不会再有第二个实例；该路径"点得动"体验仍沿用
     2026-10-03 的既有结论（待用户真机确认）。
- 备选方案（未采用）：对全部预设去掉"重新拉起"（会改动未观察到副作用的其它应用行为，风险更大）；
  托盘失败后重试托盘图标（微信托盘点击语义未确认是否为切换，可能反向隐藏，无依据不动）。

  个人路径、设备身份或语音内容。
