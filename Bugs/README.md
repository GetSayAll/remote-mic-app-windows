# Windows Bug 记录规范

## 固定流程

**非简单 Bug 必须按以下顺序处理：**

0. **先读仓库根目录的 [DEBUGGING.md](../DEBUGGING.md)（排查手册）**：同源症状判定、错误码
   字面含义不可当根因、全量聚合优先、恢复手段实验矩阵、本机环境陷阱、工具反模式清单，以及
   已经被推翻过的假设。跳过这一步的代价实测很高（2026-09-16 僵死 Bug 的调查中至少绕了三处弯）。
1. 记录可重复触发条件、实际错误和正常边界；
2. 先做**全量**聚合（按小时 / 按进程 / 按爆发轮次切分），再决定读哪一段日志；区分最终结果
   与中间事件；
3. 根据复现和日志缩小代码范围，明确根因假设并用最小实验验证；**恢复类问题必须逐项做实验
   矩阵并记录结果**（"手段执行成功" ≠ "故障被解除"，要用同一判据复查）；
4. 只修复已确认根因；
5. 重新执行原始复现并覆盖受影响的稳定基线；
6. 修复必须带一条能自动跑的测试（单元 / 契约 / 端到端至少其一），否则该规则下次还会被漏掉。

模拟硬件、单元测试、构建和安装器检查只能证明各自边界；没有真实 Windows、RC001/RC003 或第三方工具时，状态必须写为 `deferred`。

## 记录模板

每个 Bug 使用 `YYYY-MM-DD-short-name.md`，至少包含：

```markdown
# 标题

- 发现日期：
- 状态：调查中 / 已修复 / 等待真机验证 / 已归档
- 影响范围：版本、Windows 版本、RC001/RC003、第三方工具
- 功能点：模块或用户功能
- 现象：一句话描述错误行为
- 复现条件：
- 正常预期：
- 证据：日志时间段、命令、提交或测试手册
- 根因：已确认事实与仍未知边界
- 修复：最小改动及文件
- 验证：命令、观察结果和 `passed|failed|deferred`
- 隐私检查：确认未包含个人路径、设备身份、语音内容或凭据
```

历史资料不足时明确写“未知”，不得用推测补齐证据。Bug 文档和日志附件均须脱敏。
