# ADR 0002：按键注入采用双轨架构，驱动级注入作为可选 Helper

- 状态：Accepted（2026-09-23 修订 §3，见「修订记录」）
- 日期：2026-09-04
- 修订：2026-09-23

## 背景

按住说话快捷键真机验证发现：豆包输入法（固定"长按右 Alt"）与微信输入法（用户配置 左 Ctrl+左 Win）均不响应 SendInput 注入（见 Bugs/2026-09-04）。独立探针证明注入在系统层真实到达（GetAsyncKeyState 观察到按下/释放全程保持），因此判定为 IME 对模拟按键（LLKHF_INJECTED 标记）的过滤，而非本仓库注入实现缺陷。

参考实现为解决同一问题均引入了提权/驱动组件：ZSTDJan 要求管理员权限 + Frida HID 旁路；Voice_VibeCoding 的语音键注入优先 WinUHid 虚拟键盘驱动，SendInput 仅作互斥降级。

普通按键映射面临同类约束：RC001/RC003 作为 BLE HID 键盘，原始按键会到达前台程序，公共 API 无法按设备全局吞键；Raw Input 自动串联 SendInput 存在重复输入风险（路线图阶段 C），真机确认前保持关闭。

产品规划上，后续将持续自定义更多按键映射。逐点修补无法同时覆盖"IME 过滤注入"与"原始按键重复"两类问题，需要一次性的注入架构选型。

## 决策

1. 双轨注入架构：
   - 默认轨（主程序，普通用户权限）：现有 SendInput 批量注入，覆盖接受模拟按键的目标，不新增依赖；
   - 增强轨（可选 Helper，独立进程、显式安装、UAC 提权）：
     - 全局按设备过滤并吞掉 RC001/RC003 原始按键事件，消除映射重复输入；
     - 以虚拟键盘驱动执行按住说话快捷键与按键映射注入（事件与物理按键等价、无注入标记），覆盖过滤模拟按键的 IME 与应用。
   - Helper 未安装、失败或被禁用时，基础语音与基础按键不受影响（AGENTS.md Helper 边界）。
2. 驱动来源按序评估：审计 WinUHid（源码可得性、许可证、签名状态、作者授权）→ 基于微软公开样例自研虚拟 HID（承担 attestation/WHQL 签名成本）→ 暂缓增强轨（保持默认轨交付）。
3. 驱动级注入不进入基础路径；~~不使用 Frida；不继承未经审计的第三方二进制~~ → 已由 2026-09-23 修订取代：
   允许使用注入框架（含 Frida Gadget）作为增强轨的脚本载体，但必须固定版本、校验哈希、登记来源与许可，
   且仍不得继承来源不明或未审计的第三方二进制。详见「修订记录」。
4. Helper 实现的前置条件（按序）：
   - ~~真机物理按键对照：确认豆包/微信输入法在物理组合键下可唤起（区分 IME 自身问题与注入过滤）~~（2026-09-04 已完成：物理按键可唤起、注入不可，确认注入过滤）；
   - 真机确认 RC001/RC003 Keyboard/HID 事件形态（既有 TODO，决定吞键策略）；
   - 两项通过后进入 Helper 设计、驱动审计与签名流程。

## 结果

- 正面：一次架构决策同时覆盖"IME 过滤模拟按键"与"映射重复输入"，为后续任意按键自定义提供与物理按键等价的注入能力；架构落在既有 Helper 边界内，不修改基础路径承诺。
- 代价：驱动审计、授权与签名成本高，发布周期变长，新增一个需要长期维护的特权组件；Preview 阶段继续以默认轨交付，增强轨为显式可选安装。

## 修订记录

### 2026-09-23：解除原 §3 的「不使用 Frida」限制

- **决策**：产品负责人要求移除"不使用 Frida"这类阻塞性约束。原 §3 的前半句保留（驱动级注入不进入基础路径），
  后半句的"不使用 Frida"废止。
- **原因**：RC003（小米蓝牙遥控器 2 Pro）的返回 / 音量± 三个键在 Windows 侧零事件——真机取证已确认
  **设备确实上报**（usage `0x80`/`0x81`/`0xF1` 声明在键盘页 `report_id=0x01`，与可用的 确定`0x28` / 主页`0x4A`
  同处一个报告），是 **`kbdhid` 的 HID→VK 映射表缺这三个 usage 才在映射阶段丢弃**。
  唯一既能按设备源头捕获、又不需要内核驱动的落点是 **承载该设备的 `WUDFHost.exe` 内部的报告层**，
  而该落点的物理前提已在本机实测成立（宿主 PID 可从 `Device Parameters\WUDFDiagnosticInfo\HostPid` 读取，
  且为独占 RC003 宿主）。这一路径的载体必然是"注入到系统宿主进程内的脚本运行时"，参考实现即用 Frida Gadget。
- **新边界**（取代原 §3 后半句）：
  - HID 宿主内报告层捕获（即下方"增强轨"的一种实现）**属可选增强轨**，与 §1 的 Helper 边界一致，
    **不进入基础路径**；Helper 未安装 / 失败 / 被禁用时基础能力不受影响。
  - 注入框架可以使用第三方实现（含 Frida Gadget），但必须**固定版本、校验 SHA256、记录来源与许可**
    （登记到 `ATTRIBUTION.md`），并在发布前完成许可与安全审计。
  - **仍不得**继承来源不明或未审计的第三方二进制。
- **同步收窄 R5 的口径**：`docs/investigations/2026-09-22-per-device-key-interception-route-selection.md` §1 的
  R5「不引入新的系统级改动」明确为禁止内核驱动、Secure Boot / 测试签名 / 驱动签名策略、注册表过滤项与重启；
  **显式安装、可逆卸载、经用户一次性授权的提权 Helper（含固定计划任务）不属于被禁范围**。
- **证据**：`docs/investigations/2026-09-23-zstdjan-hid-host-tap-implementation-review.md`（机制复核与代价）、
  `docs/investigations/2026-09-23-rc003-hid-host-readonly-tap-result.md`（报告层只读实证，`passed`）、
  `docs/investigations/2026-09-23-rc003-hid-host-write-tap-result.md`（写入 / 拦截实证）。
- **仍未决**：R6（不降低可靠性）对应的边沿配对 / 接管就绪门 / 租约 / tap 失联 fail-safe 验收，以及 RC001 的适配
  （RC001 走厂商键 `VK 0xFF`，机制不同，不能由 RC003 外推）。
