## 1. 为什么还需要这一段

第 ① 段（提权助手 + Gadget agent）证明了**能拿到**三键、**能吞掉**它们。但"吞掉"和
"重新映射"之间曾经缺一整段：

```
设备 → WUDFHost 报告层 ──[① 捕获]──> 提权助手 ──[② 传输]──> 主程序 ──[③ 重映射]──> 动作
                                        ↑                     ↑
                                  边沿到此为止          引擎一直收不到输入
```

在接线之前，助手的 `handle_line` 收到 `{"type":"edge"}` 只做两件事：
`session.edges.push(record)` 与写日志。全库**没有任何**向主程序转发的通道
（无 pipe、无命名管道、无 IPC、无共享内存）。因此三键的实际功能状态是
**"能配置但按下去没反应"**：配置层、引擎、UI 画布早就有这三个语义键
（`RemoteButton::{Back, VolumeUp, VolumeDown}`），只是永远等不到输入。

**这一段不是可选项**：主程序侧的 Raw Input 与键盘钩子同样拿不到三键——那正是
`kbdhid` 丢弃的直接后果。边沿只能由助手主动送过来。

## 2. 方向选择：为什么是「主程序监听、助手回连」

两个方向都试过论证，结论是单向的：

| 方案 | 权限前提 | 结论 |
| --- | --- | --- |
| 助手监听、主程序连接 | 主程序需读到助手写的令牌/端口 | **不成立**。助手以管理员运行，运行时目录在 `%ProgramData%\SayAll\rc003-helper`；普通权限的主程序既读不到那里的写入，也不该去猜 |
| 主程序监听、助手回连 | 助手需读到主程序写的描述文件 | **成立**。主程序写在 `%LOCALAPPDATA%\SayAll\`，提权助手读用户目录无权限障碍 |

附带好处：主程序侧用 **随机端口**（`bind(127.0.0.1:0)`）而非固定端口，
天然避免"固定端口被别的进程占住导致桥接起不来"。

**跨账户兜底**：若提权用的是*另一个账户*的凭据（而非当前账户的提升形态），
助手的 `%LOCALAPPDATA%` 会指向那个账户。此时助手按**固定相对路径**
枚举 `C:\Users\*\AppData\Local\SayAll\rc003-bridge.ini`，取最近修改的一份
（`find_app_bridge_elsewhere`）。只读、路径固定、不递归。

## 3. 协议

ASCII 行协议，`\n` 结尾。主程序为服务端，助手为客户端。

| 行 | 方向 | 含义 |
| --- | --- | --- |
| `HELLO <ver> <token> <helper_pid>` | 助手 → app | 鉴权；**必须首行** |
| `OK <ver>` / `DENY <reason>` | app → 助手 | 鉴权结果；`DENY` 累计 3 次断开 |
| `E <t_ms> <u1,u2,...>` | 助手 → app | 边沿：当前按下的 usage 集合（**十六进制**） |
| `E <t_ms> -` | 助手 → app | 边沿：集合为空 = 全部释放 |
| `P <t_ms>` | 助手 → app | 心跳（每 1 s） |
| `BYE <reason>` | 助手 → app | 助手收尾，按键即将释放 |

**边沿是绝对状态，不是增量事件。** agent 侧只在集合变化时上报当前按下的 usage 集合
（`emitEdgesIfChanged`），助手原样转发，主程序做差分转成逐按钮边沿。理由：

- 丢行自愈——丢了一条"按下"还有下一条状态兜住，不会永久错位；
- 重连自愈——断线期间的变化无从逐条补发，重连后**一份绝对状态就能完全对齐**
  （`app_bridge_worker` 在握手成功后立即重发 `last_known`）。

**usage 用十六进制**（`f1` / `80` / `81`）与日志里的 `0x00F1` 同源，
排查时不必在十进制/十六进制之间来回换算。前缀大小写都接受（`0x` / `0X`）。

描述文件 `rc003-bridge.ini` 也是 `key=value`，两侧各有独立实现
（助手零第三方依赖、手写解析；主程序侧亦然），一致性由**两侧自检**钉住：
助手自检第 26 项核对路径约定，主程序侧 `parse_descriptor` 单测核对格式。

## 4. 关键决策：投 `GateEdge`，不是 `HidUsages`

引擎有两条现成的输入路径，选错了会有副作用：

| 消息 | 引擎内部效果 | 结论 |
| --- | --- | --- |
| `HidUsages(set)` | `ButtonStateMerger::update_hid_usages` → **整体替换** `merger.hid` | 若同时有 RC001 在跑，会把 RC001 的 HID 按下状态一起冲掉 |
| `GateEdge(edge)` | `ButtonStateMerger::apply_keyboard_button_edge` → 只按键操作语义键位 | **选中** |

更重要的是 `GateEdge` 的**语义**完全对得上：RC001 上这三个键本来就以
"被吞的键盘边沿"形态走这条路（`key_gate` 的"直接归因族"：VK 0xFF 族厂商键）。
主程序桥接把助手送来的边沿投进**同一条**通道，于是：

- 引擎**一行都不用改**；
- RC003 与 RC001 在引擎下游**完全同构**（手势识别、映射查表、`SendInput` 注入、
  按住连发、泄漏对冲全部复用）；
- 泄漏对冲也自动正确：`native_pending` 表示"原生动作已进 OS"，而 RC003 三键的
  原生动作**确实没有发生**（被 tap 清空了），因此不会被误判为"原生已交付"而跳过注入。

## 5. 威胁模型（必须如实理解）

**令牌不是安全边界。** 它的作用是**防误连、防混淆**，强度只是"每次启动都不同"级别
（时间 + PID + 栈地址混合的 xorshift，**不是密码学强度**）。同用户权限的进程本来
就能读该描述文件、也能注入主进程——Windows 用户态没有能挡住它的边界。

真正需要防的场景是"**助手没在跑时，别的进程占住端口往主程序喂伪造边沿**"，
这由**方向选择**天然消解：主程序是监听方，且只接受出示正确令牌的连接。

**纵深防御在白名单**：即使令牌泄漏，桥接也只接受
`BRIDGE_ALLOWED_USAGES = [0x00F1, 0x0080, 0x0081]`，其余 usage 一律丢弃并计数
（`usages_dropped`）。攻击者最多伪造这三个键，无法借桥接触发任意按键映射——
考虑到映射动作包含"启动任意应用"，这条限制是实质性的，不只是形式。

**鉴权前不得转发**：助手侧只在 `session.authenticated` 为真时才 `push_edges`。
未鉴权的连接永远不会被续约（因此也不会清键），但它报的边沿若被转发，就等于
任何本地进程都能往映射引擎灌按键。

## 6. fail-open 合同：三层兜底

三键被清空期间，如果链路断了而没人释放，引擎会**永远以为按键还按着**
（触发长按/连发语义）。三层兜底，缺一层都会在现场变成"按键卡住"：

1. **jitter 层——助手正常收尾**：`app_bridge_worker` 退出前先发释放边沿再发 `BYE`。
   顺序不能反：先 `BYE` 的话主程序会当成"正常告别"而不再等待后续释放。
2. **看门狗层——助手被强杀**：助手每 1 s 发 `P`；主程序超过
   `SILENCE_TIMEOUT = 3 s` 没有任何行即判定链路已死 → 释放全部并断开。
   这一层是必需的：助手被任务管理器结束时不发 `BYE`。
3. **agent 租约层**：助手停止续约后 agent 在 2 s 内自行停止清键——
   **这一层保证的是"键恢复原生行为"，不是"主程序释放状态"**，两者不可互相替代。

## 7. 两个在自测里被抓到的真实缺陷

写这一段的价值在于：它们都是**编译通过、逻辑看起来对、只有构造出场景才会暴露**的类型。

### 7.1 接管竞态：用 socket 地址判断"我还是不是当前连接"

第一版把当前连接存成 `Arc<Mutex<Option<TcpStream>>>`，收尾时**无条件** `take()`。
后果：新连接刚接上就被旧连接的收尾清掉 → 新连接下一轮认为自己被替换、主动让位 →
**两个连接互相让位，桥接整体哑掉**。现场表现是"助手重启以后再按三键毫无反应"，
而日志上两边都只是安静退出，什么错误都没有。

修法：`current` 改成带**自增编号**的 `CurrentConn { id, stream }`，
`is_current` 按编号判断，收尾时只清理"如果当前连接还是我"。

不能用 socket 地址替代编号：连接被 `shutdown` 后 `local_addr()` 会失败，
地址比较退化成"谁都不是当前"，同样误判。这个坑在
`replacement_takes_over_and_survivor_keeps_working` 里被构造出来。

### 7.2 串行 accept 让"接管"永远不触发

第一版 `accept_loop` 里直接串着 `handle_connection`（阻塞到该连接结束）。
于是**旧连接没结束之前新连接根本不会被 accept**——"后来的助手顶掉旧连接"
这段代码永远不会执行。

自测里 beta 收不到 `OK`（`read_line` 超时）就是这么暴露的。修法：每个连接交给
独立线程，监听线程立刻回到 accept。这不是为了并发（预期只有一个助手），
而是**接管语义能成立的前提**。

### 7.3 被接管方不得释放状态

与 7.1 配套：`replaced` 退出的旧连接**不执行释放**，也不改写共享状态。
它手里那份按下状态已经归接手方所有，释放会误伤接手方刚建立的按下状态
（表现为"刚按下就被松开"）。接手方收到绝对状态会自行重建；即便它什么都不发，
它自己的静默看门狗也会兜底。

### 7.4 测试自身的缺陷

`silence_watchdog_releases_pressed_buttons` 第一版用 `drop(stream)` 模拟"助手被强杀"——
但 reader 持有同一 socket 的另一个句柄，只丢一个引用连接并不会断开，
服务器读不到 EOF，"被强杀"这个场景根本没被构造出来。改为 `shutdown(Both)` 后通过。
**测试写错方向比不写测试更危险**：它会给出一条本来不存在的信心。

## 8.5 真机首跑（E7 第一轮，2026-09-23 18:36）：主程序侧没生效 + 一个错误码缺陷

**结果：E7 未通过；原因不在桥接代码，而在"跑的主程序不是这一版"。**

助手那一轮的日志（`hardware/RC003/evidence/helper-run.log` 18:36:42 起）：

```
[APP-BRIDGE] event=enabled descriptor=C:\Users\hd838\AppData\Local\SayAll\rc003-bridge.ini
[APP-BRIDGE] event=unavailable reason=descriptor_path_unknown tries=1 …
```

**三条独立证据指向同一结论**（主程序侧那一版不含桥接）：

1. `target/debug/sayall-windows-app.exe` 的 **mtime 是 02:11**，而接线提交是 18:26。
2. 主程序诊断日志（`%LOCALAPPDATA%\SayAll\Logs\sayall-diagnostic.log`）里
   **一条 `rc003_bridge` 记录都没有**——桥接启动时必打 `phase=listening`，
   没有记录就等于那段代码从未执行过。
3. `%LOCALAPPDATA%\SayAll\` 下只有 `Logs\`，**没有** `rc003-bridge.ini`。

**教训（可迁移）**："在应用侧没看到效果"有两个完全不同的原因——**代码没生效**与
**代码有 bug**。在怀疑代码之前，先证明**跑的是哪一版二进制**：比对 exe 的 mtime、
读日志里的 `source_revision`、再看"启动时必打的那条日志"有没有出现。
本次若不先做这一步，会直接去查协议并白查一轮。

**同轮暴露的错误码缺陷（已修，自检第 28 项钉住）**：`reason=descriptor_path_unknown` 是错的。
当时的实现是 `.filter(|p| p.exists()).or_else(兜底搜索)`，于是"描述文件不存在"
被折叠成"路径未知"，而**同一行的 note 却写着"主程序未运行属正常现象"**——
两句话自相矛盾，且 reason 会把排查方向引到"路径配置错了"。
这属于本项目反复出现的同一类问题：**错误码把两类原因合并，让证据指向错误方向**。

修法：不做 `exists` 预筛，把"文件不存在"交给 `bridge_connect` 用
`descriptor_missing(<完整路径>)` 如实表达（原因与路径一起打出，可直接核对）；
跨账户兜底搜索改为**限频 30 s**（原写法会每 2 秒枚举一次 `C:\Users\*`）。
