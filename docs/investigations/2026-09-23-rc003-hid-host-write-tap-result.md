## 1. 要验证的命题

只读实验回答的是"报告里有没有三键"。本文回答下一问：

> **我们在 `onEnter` 写入报告缓冲区的字节，是否被 Windows 的键码翻译（`kbdhid` → 键盘栈）采纳？**

这个问题决定了路线 A 能否落地：如果写入不被采纳，则"清空 + 应用侧重映射"的整个方案不成立；
如果被采纳，则该路线在报告层具备**按 usage 拦截**的能力（正面证据是"改写后下游看到了我们写入的内容"）。

**"写入成功"不能只有探针自述。** 因此必须有 Windows 输入层的独立观测，且要有对照——
这正是 2026-09-22 那次"层错位"判定栽的坑（拿 Raw Input 的观测去否证一个不读 Raw Input 的方案）。

## 2. 方法：两条独立通道交叉验证

| 通道 | 位置 | 作用 |
| --- | --- | --- |
| 宿主侧（写入方） | `WUDFHost.exe` 内挂 `ntdll!NtDeviceIoControlFile` | 命中 `IOCTL 0x80018483`（in 8 / out 9）时改写 / 擦除报告，记录 `orig→new` 与回读值 |
| Windows 侧（观测方） | 同一进程内的 Raw Input 后台监听（`RIDEV_INPUTSINK`） | 按 `hDevice` 做**设备归属**，只统计来自 RC003 的键盘事件 |

两侧记录都带毫秒 epoch 时间戳（同一时钟域），可逐条配对。

**写入面**：只动 9 字节键盘报告的偏移 3..8（三个 16 位小端 usage 槽），
绝不触碰 `report_id` / `modifiers` / `reserved`（报告结构取自只读实测日志，不是推断）。

**零残留**：`onLeave` 把原始字节写回；若发现内核在调用期间改写过缓冲区，则放弃回写并上报
`kernel_changed=true`（该计数本身上报为证据，而不是被静默吞掉）。

## 3. 阶段设计（要害在于把"零事件"变成有意义的证据）

| 阶段 | 报告层动作 | 操作 | Windows 侧期望（仅 RC003） | 这条要达到什么 |
| --- | --- | --- | --- | --- |
| `pre` | 只观察 | 唤醒遥控器 | — | 预热，避免唤醒动作被算进 `A` |
| `A` | 只观察 | 确定 ×2 | `VK_RETURN` | **阳性对照**：证明观测通道确实能读到本设备 |
| `B1` | 目标 usage → `0x0028` | 返回 / 音量± | `VK_RETURN` | 改写被采纳（该键改前零事件） |
| `B2` | 目标 usage → `0x0068`(F13) | 返回 / 音量± | `VK_F13` | **无歧义**改写证据：本机没有任何自然来源会产生 `VK_F13` |
| `C` | 仅擦除目标 usage | 音量± + 确定 ×1 | 目标键 0 事件；确定 仍 `VK_RETURN` | 选择性擦除不波及非目标键（产品可保留 确定/主页 原生行为） |
| `D` | 三个 usage 槽全清 | 确定 ×2 | **0 事件** | **与 `A` 同键对照**：唯一差别是我们写了字节 ⇒ 擦除生效 |
| `E` | 停止写入（回到 observe） | 确定 ×2 | `VK_RETURN` | 无残留：停止改写后按键恢复原状（`disarmed` 标志本身另见 §4.8） |

- `A` 与 `D` 必须是**同一个键**。单独看 `D` 的零事件毫无信息量——目标三键在只读基线里本来就是零事件。
- 判据（由 `wudf_ioctl_write.py` 从原始记录重算，不依赖任何汇总字段）：

| 判据 | 条件 | 不满足时的退出码 |
| --- | --- | --- |
| `A_control_present` | `A` 阶段 RC003 的 `VK_RETURN` 按下 ≥1 | 8（观测通道不可信，其它阶段一律作废） |
| `B1_rewrite_effective` | `B1` 阶段 `VK_RETURN` ≥1 **且**宿主侧确实发生过改写 | 9 |
| `D_erase_effective` | `D` 阶段有改写 **且** RC003 事件数 = 0 | 10 |
| `E_restored` | `E` 阶段 `VK_RETURN` ≥1 | 11 |
| `B2_rewrite_f13` | `B2` 阶段 `VK_F13` ≥1 **且**宿主侧确实发生过改写 | 12 / 13（见下） |
| `C_target_erased_at_layer`、`C_collateral_ok` | `C` 阶段有改写；非目标键未被波及 | —（信息项） |

`B2` 不满足时有**两种语义完全不同**的情况，必须分开：

| 退出码 | 判定 | 含义 |
| --- | --- | --- |
| 12 | `phase_not_observed` | 窗口内**零命中** ⇒ **采集缺失**（操作层），补采即可，不是机制失败 |
| 13 | `substitute_not_mapped` | 已发生改写但下游无对应按键 ⇒ **技术结论**：该 usage 在本机未被映射，替换键须逐键实测 |

判定只针对**本次实际执行过的阶段**（由日志「阶段时间轴」段解析）：补采时未跑的阶段标 `SKIP`，
既不通过也不失败。

### 4.4 三条已成立的结论

**① 擦除生效（同键对照闭合）**。`A` 与 `D` 是同一个键（确定）、同一台设备、同一次运行：
`A` 有 4 条事件、`D` 有 0 条，而**唯一差别**是我们在报告层写了字节
（`A` 命中 4 次/改写 0 次，`D` 命中 4 次/改写 2 次）。单独看 `D` 的零事件没有信息量
（目标三键在只读基线里本来就是零事件），是这个对照使它成为证据。

**② 改写被翻译层采纳（`B1`）**。4 次改写把 返回/音量+/音量- 变成 `0x0028`，Windows 侧随即出现
4 次 `VK_RETURN`，**一一对应**。这条推理在日志内闭合、不依赖操作假设：

- 改写前这三个键在 Windows 侧是零事件（只读实验已实测）；
- `B1` 期间宿主侧**没有任何**未被改写的 `0x0028` 报告——若用户按了确定，会留下
  `orig=0100002800…`、`mutated=False` 的条目，而日志里不存在这样的记录；
- ⇒ 这 4 次 `VK_RETURN` 只能来自我们写入的字节。

**③ 改写无歧义证据（`B2`）**。把目标 usage 写成 `0x0068`(F13)，Windows 侧出现 4 次 `VK_F13`。
`VK_F13` 在本机没有自然来源（无此物理键、无软件绑定），且 `B2` 期间宿主侧不存在未被改写的
目标键报告 ⇒ **写入内容被翻译层直接读取**，不存在"Windows 恰好也认原值"的替代解释。

⇒ 写入发生在 Windows 键码翻译**之前**，路线 A 的机制前提与写入路径均成立。

**顺带成立的一条产品约束**：`0x0068` 可作替换键（未触发退出码 13）。
但**不能推广**——不同替换 usage 是否可映射仍须逐键实测，判定器已把这个约束编码为
`13 substitute_not_mapped`。

### 4.5 指纹级旁证：扫描码也是从改写后的 usage 推导出来的

Raw Input 的 `RAWKEYBOARD.MakeCode`（即 PS/2 扫描码）在四种情形下的取值：

| 情形 | 报告 usage | `VKey` | `MakeCode` |
| --- | --- | --- | --- |
| 原生 确定（`A`，两轮） | `0x0028` | `0x0D` | `0x1C` |
| 改写 确定（`B1`） | 写入 `0x0028` | `0x0D` | `0x1C` |
| 改写 F13（`B2`） | 写入 `0x0068` | `0x7C` | **`0x64`** |
| `SendInput` 注入 F13（观测通道自检） | — | `0x7C` | **`0x00`** |

`MapVirtualKeyW(VK_F13, MAPVK_VK_TO_VSC) = 0x64`、`VK_RETURN = 0x1C`，与上表逐条吻合。

含义：

- `kbdhid` 不是"顺带读到了我们改的 usage"，而是用**改写后的 usage 重新走完了整条
  HID usage → (VK, PS/2 扫描码) 推导**。写入被消费在翻译链的**最上游**。
- `0x64` 具备指纹性质：`SendInput` 注入的事件不带扫描码（实测 `0x00`），
  本机也没有别的来源能产生 `VK_F13` ⇒ 这条记录不可能由"我们的写入"以外的路径产生。
- 产品含义：替换键会得到**正常的扫描码**，因此对按物理键位/扫描码响应的应用
  （游戏、部分输入法、低级键盘钩子）同样有效——不是"只有一个 VK 能用的半成品"。

### 4.6 `B2` 首轮为何未采到（已由补采闭合）

首轮 `B2` 窗口内宿主侧命中 **0 次**——一个报告都没有经过钩子。同期钩子仍然存活
（紧随其后的 `C` 阶段立刻恢复到命中 10 次），所以不是钩子失效，而是**窗口内没有按键**。
属操作层缺失，不是技术结论；补采后该阶段 PASS。

**为何值得单独补 `B2`**（而不止步于 `B1`）：`B1` 把 usage 改成 `0x0028`，而 `0x0028` 本身也是
设备上的有效 usage，理论上留有"Windows 恰好也认这个值"的替代解释空间（虽已被 §4.4 的推理排除）。
`B2` 用 `0x0068`(F13) 把这条路封死；同时它也探明了"替换键可用"这条产品约束（§4.4 末）。

### 4.8 本轮发现并修正的两处装置缺陷（都已修）

**① 判定层：非关键断言失败被静默算进"通过"。**
首轮判定器对 `B2` 报了 `FAIL` 却**仍返回 `0`**——它只在关键链上短路，对"非关键断言失败"
没有任何反馈。修正后：

- `verdict(active=…)` 只对**实际执行过的阶段**判定，未执行标 `SKIP`；
- `detect_phases()` 从日志「阶段时间轴」段解析执行范围——唯一权威来源；
  只按记录推断会漏掉零命中的阶段，而那正是最需要如实标注的对象；
- `--analyze` 支持多份日志**合并判定**：全程日志 + 补采日志合并后与一次跑满全程等价；
- 退出码区分 `12 phase_not_observed` 与 `13 substitute_not_mapped`；
- 分析层自检扩到六例（全程通过 / 对照缺失 / 擦除未生效 / 补采通过 / 补采零命中 /
  补采有改写无 F13），退出码 `0/8/10/0/12/13` 全部符合期望；合成日志带时间轴段，
  自检覆盖 `detect_phases → verdict(active)` 整条链路。

**② 收尾覆盖缺口：自动解除武装这条 fail-safe 从未被观测到触发。**
两轮日志的最终统计都读到「解除武装=False」。查根因：agent 只在「计划表总时长 +
`GRACE_MS`(3000)」之后才把 `disarmed` 置真，而收尾只等 1.5 秒就取统计 ⇒ 该字段**恒为 False**，
"计划表走完即自动停写"这条 fail-safe 实际上**一次都没有被验证过**。修正：Python 侧新增与 JS
对齐的 `GRACE_SECONDS`，收尾等过宽限期再取统计，且若届时仍未置真则**主动提示**。

→ 这两份日志产生于修复之前，其中的「解除武装=False」**不代表有残留**：步骤 6/6 随后
detach 卸载整个注入脚本，且 `E` 阶段已实测按键恢复；但"自动解除武装"本身仍需在下次运行时
才算真正验过。

### 4.9 当前状态

**7/7 通过。路线 A 的机制前提与写入路径均已由真机实测确立**：报告层的擦除与改写都会被

- **共享宿主路径**、**严格 EDR/HVCI 策略**；
- **RC001 适配**：RC001 走厂商键 VK `0xFF`，与本路线机理不同，**不可外推**。

## 5. 契约、代价与风险

- **需一次交互式 UAC 提权**（宿主在 session 0，普通权限 `OpenProcess` 返回 `err=5`）。
- **不装内核驱动、不改 Secure Boot / 测试签名 / 驱动签名策略、不写注册表、不装计划任务、不需重启**。
- 计划表走完 + 3 秒宽限期后 agent **永久解除武装**；写入次数有上限（`MAX_MUTATIONS=400`）；
  进程退出即卸载注入脚本。
- 唯一系统级副作用：`rewrite` 阶段把目标键变成 确定(Enter) 或 F13 —— 运行期间应把焦点留在桌面或空白区域，
  不要停在文本编辑器里（`F13` 无任何应用响应，`Enter` 在桌面上无动作）。
- 最坏情况：宿主异常崩溃 → Windows 自动重启宿主并重新枚举设备（遥控器重连即可），**不需要重启电脑**。
  本机该宿主核验为**独占 RC003**，不承载其它设备。
