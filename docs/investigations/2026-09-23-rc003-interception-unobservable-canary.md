## 1. 问题：准备验收时发现判据本身没有分辨力

在准备 `run` 模式（拦截生效）验收时，逐条核对 E2 的判据：

> E2 通过判据 = 无原生字符、无光标/音量变化、锁屏不出现协议选择器。

这三条在 **RC003 上恒为真**，与代码是否生效无关。原因是已经定论的事实：

> RC003 的返回 / 音量± 三键（usage `0x00F1` / `0x0080` / `0x0081`）在 Windows 侧**本来就零事件**。
> 设备确实上报了，但 Windows 的 HID→VK 映射表缺这三个 usage，`kbdhid` 在映射阶段丢弃。

于是：

- 清空生效 ⇒ 三键被清掉 ⇒ Windows 收不到 ⇒ **无现象**
- 清空完全没生效 ⇒ 三键仍到达 `kbdhid` ⇒ 仍被丢弃 ⇒ **无现象**

**两种情形的外部表现完全一致。** 更糟的是，`observe`（一个字节都不清）与 `run`
在用户可感知层面也无法分辨——也就是说，此前所有真机证据（都来自 `observe`）
在逻辑上**无法**支持「拦截生效」这一结论，无论跑多少次。

这不是实现缺陷，是**判据缺口**：验收方案里写下的判据无法区分「通过」与「没跑到」。
若按原判据执行并签字，会得到一个**恒真但无信息量**的「passed」。

## 2. 处置：哨兵键（canary usage）

思路是给验收装一个**对照物**：清一个 Windows **本来能处理**的键，让「清空」这件事产生现象。

RC003 上天然合适的候选是**主页键 usage `0x4A`**：它与三键在**同一个 `report_id=0x01`** 内
（所以不需要扩展平台能力），而 Windows 认识 Home，记事本里按下会跳到行首。

接口：助手新增 `--canary-usage <U16>`（十六进制、逗号分隔、可重复）；
新入口 `run-helper-canary.cmd` 默认传 `0x4A`。

三步对照：

| 时刻 | 现象 | 证明了什么 |
| --- | --- | --- |
| 运行前按主页（记事本） | 光标跳到行首 | 基线：该键确实可达。**阳性对照，不可省** |
| 运行中按主页 | 什么都不发生 | **清空真的作用到了报告上** |
| 结束 / 租约到期 / Ctrl+C 之后 | 光标又能跳 | **fail-open 生效**：不残留清空、不需重启 |

第二条与第三条合起来，把 E2（清空消除原生动作）与 E4（失效与恢复）从**推断**变成**直接观察**。

**为什么基线不可省**：少了它，「按主页无反应」也可能是设备掉线、宿主换了、键本身不可用
——这些都与清空无关。基线与对照必须在**同一台设备、同一轮会话**内取得。

### 安全边界

- 只清该 usage 的 **2 个字节**；`report_id` / `modifiers` / `reserved` 一律不碰。
- 仍受 `--duration` 上限与 agent 侧 **2 s 租约**双重兜底（助手死亡 ⇒ 最迟 2 s 停止清键）。
- **默认关闭**；只有显式传 `--canary-usage` 才生效。
- 参数错误在**做任何事之前**以退出码 2 结束（避免清空范围被一条畸形参数改坏）。

## 3. 两个集合必须分开

哨兵键**只进清空集合、不进上报集合**。否则日志里出现一个 usage 的边沿时，
无法分辨那是三键还是哨兵——用错误探针污染正确证据。

agent 侧因此拆成两个变量：

| 变量 | 语义 | 可否被下行修改 |
| --- | --- | --- |
| `reportUsages` | **上报**集合，恒为三键 | **不可**（护栏拒绝） |
| `clearUsages` | **清空**集合，默认三键 | 可，但只允许「追加」 |

下发走 **命令** `{"type":"targets","report":[…],"clear":[…]}`，随 `arm` / `mode` / `restore`
一并发给已鉴权的会话。**不能走 `config`**：接管轮 agent 早已启动，不会重读
`frida-gadget.config`——走 config 的话这条功能在接管路径上会静默失效。

心跳里新增 `report_usages` / `clear_usages` 两个字段：验收时一眼能看出 agent
**实际**在用哪个集合，此前这只能靠助手侧推断。

## 4. 协议护栏（也是「隐形配置」的防线）

`targets` 命令两条护栏，越界一律拒绝、且**不改动现有清空范围**：

1. **`report` 必须恰好等于三键。** 否则等于允许远端关掉上报——那样「看不到按键」
   会被误读成「按键没到」，而实际上是被配置屏蔽了。这是最危险的一类误判。
2. **`clear` 必须是 `report` 的超集。** 否则会出现「报了但不清」的隐形配置：
   日志显示已武装，实际每个键都放行。

只有「追加哨兵键」这一种改变被允许——这正是验收需要的形状。

## 7. 可迁移的教训

1. **验收前先问「这条判据能不能失败」。** 若一个判据在「功能生效」与「功能没跑到」两种
   情形下都返回同一个结果，它不是判据，是噪音。本轮 E2 的原始判据正是如此。
2. **平台事实会同时杀掉功能与判据。** 同一个原因（`kbdhid` 丢弃三个 usage）既让三键不可见，
   也让「按键不可见」这条判据失去分辨力——修复功能时容易忽略判据也被一并破坏了。
3. **给验收装对照物。** 无法观察的过程要人为制造可观测量（这里是清一个本来可用的键），
   而不是退回到「看日志字段对不对」——日志字段只能证明我们**打算**做什么。
4. **基线阳性对照要与实验同源**（同设备、同会话）。跨设备或跨轮次的对照不能排除
   设备/宿主变化这些混淆因素。
5. **功能开关不能走启动期配置**，如果存在「不重启就接管」的路径——那种情况下配置
   永远不会被重读，功能会静默失效，而且日志上看不出来。
