## 4. 但这次运行也暴露了两处「安全上限失效」

两条都是**我写下的承诺，实际不成立**。它们的共同特征是：只有在真机、且运行足够久之后才会显形；
自检与静态检查都抓不到（此前只覆盖"功能路径"，不覆盖"收尾路径"）。

### 4.1 `--duration` 在会话存活期间**永不生效**

- **现象**：启动器传的是 `--duration 300`，日志在 `up=518s` 时仍在写入，
  进程 `rc003-helper.exe 29964` 确认仍在运行。
- **根因**：会话读取用阻塞的 `BufReader::lines()`，而 `--duration` 的检查只写在主循环里，
  主循环又被**同步调用**的 `serve_connection` 阻塞 → 只要 agent 连着，检查点就永远到不了。
- **为什么危险**：`--duration` 是"不把钩子留在系统上"的主要保障。它在**正式拦截模式**下失效，
  意味着三键会一直被清、超出预期时间。唯一还兜住的是 agent 侧租约——**设计上它只是最后一道防线，
  不该成为唯一一道**。
- **修法**：给 socket 设读超时（`READ_POLL_MS = 250`），会话循环改成"轮询式读"，
  并把 `--duration` 的**绝对到期时刻**传进 `serve_connection`，让它自己判断退出；
  收尾逻辑仍只在主循环一处，保持单一出口。

### 4.2 Ctrl+C / 关窗**不会**发 `disarm`

- **现象**：源码里从未调用过 `SetConsoleCtrlHandler`（全程只有 0 处）。
- **后果**：Ctrl+C 与关窗都会让系统**直接终止进程**，`main()` 末尾那段"发 disarm 再退出"的
  收尾代码永远执行不到；日志与 `--help` 里写的"会先给 agent 发 disarm"是空的。
- **修法**：安装控制台处理器（`CTRL_C / BREAK / CLOSE / LOGOFF / SHUTDOWN` 均置位，返回 1 不清场），
  由主线程收尾。注册失败会打 `[WARN]`（不致命，租约仍在）。

### 4.3 运行自己给出的判决：收尾代码一行都没执行过

这次运行的**结束方式本身就是证据**。对归档日志做关键词计数：

| 关键词 | 出现次数 | 应为（若收尾正常） |
| --- | --- | --- |
| `[TIMEUP]` | **0** | 1（`--duration` 到期） |
| `[DISCONNECT]` | **0** | 1 |
| `[SUMMARY]` | **0** | 1 |
| `已向 agent 发送 disarm` / `[NOTE]` | **0** | 1 |
| 最后一条心跳里的 `disarmed` | `false` | — |

日志停在 `[HB] up=518s`，其后**没有任何一行**。也就是说：`main()` 里从 `[TIMEUP]` 到
`[SUMMARY]` 的那整段收尾代码，在这次运行中**一次也没被执行**（两处缺陷叠加的结果），
进程是被系统硬终止的。

> 这一点值得单独指出：如果没有把日志归档下来做这次计数，"跑完了"和"跑崩了"
> 在表面上完全一样——都只是窗口关掉了而已。
> 附带说明：归档快照与最终日志**逐字节相同**（140 492 字节），即本次归档是完整的一次运行。

## 6. 这次**没有**证明什么（边界）

1. **没有证明"拦截生效"**。`observe` 不清任何报告，`clears_ok=0`。三键在 Windows 侧
   本来就是被 `kbdhid` 丢弃的，所以"按下去没反应"在本次运行里是**预期现象**，不是证据。
   真正的判据在 `run` 模式：清掉三键 usage 后，由应用侧动作代替。
2. **没有检验"确定 / 主页 / 方向键无回归"**。什么都没碰，所以"没有回归"是构造上的必然，
   不构成证据。这条必须在 `run` 模式下测。
3. **`--duration` 修复后的真机行为未复验**。自检覆盖的是真实的 `serve_connection` 函数，
   但"与活 agent 联动、打 `[TIMEUP]` 并撤钩"缺一次真机确认。
4. **Ctrl+C 的端到端行为未自动化验证**（自检里发 CTRL_C 会把自己杀掉），
   本次只验证到"处理器能注册成功"。
5. **注入不随助手退出而卸载**。Gadget 常驻在宿主 `WUDFHost.exe` 内直到该进程重启；
   此时 agent 已随租约失效而停止清键，功能上是惰性的，但"进程里多了一个已加载 DLL"
   这一点属实，应在 R8 / 产品化评审里如实登记。
   > **2026-09-23 追加**：这条"常驻"不只是审计项，它**直接导致了下一次运行失败**——
   > 那份被映射的 DLL 锁住了运行时目录，而当时的运行时准备是无条件覆盖复制。
   > 见 [`2026-09-23-rc003-helper-rerun-blocked-by-locked-gadget.md`](2026-09-23-rc003-helper-rerun-blocked-by-locked-gadget.md)。
   > 教训：登记"残留"时，要顺手问一句"这个残留会不会改变别的路径的前提"。
