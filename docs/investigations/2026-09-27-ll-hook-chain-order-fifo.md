# LL 键盘钩子链的调用顺序是 FIFO（最早安装最先调用）——"链头 bump" 前提不成立

- 日期：2026-09-27
- 状态：本机实证（可复现实验：`cargo run --example hook_order_probe -p sayall-windows [count_first|swallow_first]`）
- 影响：`key_gate` 与 `key_suppressor` 两处长期假定的"重装钩子可抢占链头"策略；按住说话快捷键录入
  无法记录输入法（微信输入法）语音和弦的原因

## 实验

同一进程内安装两个 `WH_KEYBOARD_LL` 钩子：
- A = 吞键钩子：吞掉注入的 VK_F13（模拟外部输入法吞掉自己的和弦键）
- B = 观测钩子：只计数（模拟本应用的录入/观测钩子）

注入 8 次 VK_F13（down+up = 16 个事件），结果：

| 安装顺序 | B（观测钩子）看到 | A（吞键钩子）吞掉 |
|---|---|---|
| B 先、A 后（`count_first`） | **0** | 16 |
| A 先、B 后（`swallow_first`） | **16** | 16 |

⇒ **先安装的钩子先被调用（FIFO）**。后安装的钩子排在链尾，只有在前面所有钩子都
`CallNextHookEx` 放行时才能看到事件。

## 推论（与真机现象逐条吻合）

1. 微信输入法随用户登录/输入法加载而安装钩子，早于本应用 ⇒ 它**永远**排在录入钩子之前，
   重新安装只会把本应用进一步推后（"链头 bump" 是反向操作）。
2. 输入法的语音和弦（用户为其选择的按住说话快捷键，如 左 Alt + 左 Win / 左 Ctrl + 左 Win）
   在到达本钩子之前已被吞掉——**物理按键对本应用的 LL 钩子不可见**（`keys_seen=0`）。
   输入法吞的是整对边沿（DOWN 与 UP），故连"只剩第一个键"也只在和弦首键被放过时出现。
3. 偶发成功（真机 07:05、08:43 两次完整捕获）对应输入法钩子**休眠期**：该输入法的热键钩子
   会休眠，需由输入法配置切换等事件唤醒（本仓库 `crates/sayall-windows/src/ime.rs` 的
   `cycle_wetype_profile()` 与 `wetype_dormancy_probe` 即为此而建）。
4. `key_suppressor` 的 F5 抑制之所以仍然有效，是因为 F5 不是输入法的和弦键，输入法放行后
   本应用的钩子（无论链条位置）总能拿到它；与"抢占链头"无关。

## 对既有实现的处置

- `key_gate`：录入开始的一次性 bump、录入期 200ms 定时 bump、每条边沿后的重抢 bump 均应移除
  （FIFO 前提下只会把钩子推后、增加无谓重装）。钩子只在平台启动时安装一次。
- `key_suppressor`：其"会话开始 + 10s 定时 bump"同属该前提；移除或保留需以 F5 实测为准
  （现有证据显示 F5 抑制不依赖它；移除可减少重装churn，但要单独回归 F5 场景）。
- 定时器 id 缺陷（`hWnd=NULL` 线程定时器忽略 `nIDEvent`，见
  `Bugs/2026-09-27-capture-preheld-keys-block-recording.md`）仍应修复——它对任何未来的
  定时逻辑都是陷阱。

## 录入输入法和弦的技术路线（结论）

LL 钩子层**无法**观测被更早安装的钩子吞掉的按键，因此可选路线只有三类：

1. **录入期间让输入法让位（推荐，应用层可控）**：把录入界面所在窗口的输入区域临时切到
   非输入法布局（或让微信输入法在该会话非活动），其和弦判定不再生效，物理边沿直达本钩子；
   录入结束后恢复。**前置验证项**：TSF/布局切换曾在本仓库出现"前台是自身 WebView 时整页
   重载"（Bugs/2026-09-12）——需实测布局切换是否触发。
2. **常驻早期钩子组件**：在输入法之前启动并安装 LL 钩子（登录早期计划任务/服务），把边沿经
   IPC 送回应用。能根治链序问题，但引入常驻组件与新的进程间契约（成本高）。
3. **冲突检测 + 引导**：录入时检测组合是否被输入法占用并提示更换（产品降级，零架构改动）。

被排除的路线：Raw Input（LL 钩子吞掉的事件不会进入 Raw Input，2026-09-05 调查实证）、
重新安装抢链头（本文实证为反效果）。
